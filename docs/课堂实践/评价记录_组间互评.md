## 1. 这段代码如何执行？

**输入**

- `POST /api/projects/:id/assign-reviews` 的 `reviewersPerSubmission`（默认 3）
- `POST /api/assignments/:id/review` 的 `scores`、`comment`
- 请求头中的 Bearer token（决定当前用户与角色）

**关键条件**

- 只有教师/管理员能分配（第 597 行 `requireMembership(..., ['teacher','admin'])`）
- 至少 2 个小组（第 599 行）
- 评审方不能是提交方本身（第 603 行 `x.id !== s.teamId`）
- 同一「提交物 + 评审组」不重复建任务（第 604 行）
- 提交互评时：任务必须属于本人所在小组（636–637）、状态必须是 `pending`（638）、不能超过截止时间（639）

**调用顺序**

1. `assign-reviews`：遍历项目的提交物 → 为每份提交物挑 `per` 个其他小组 → `insert assignments`（状态 `pending`）→ 写过程日志 → 保存
2. `GET /api/reviews/todo`：按「我所在小组」筛出 `pending` 任务，返回提交物信息与评分维度
3. `POST /api/assignments/:id/review`：校验归属与截止 → 计算总分 → `insert reviews`（`type='cross'`）→ 把任务改为 `submitted`

**会修改的数据**

- `assignments`：新增待评任务；提交后 `status='submitted'`
- `reviews`：新增组间互评记录（含 `reviewerId`，前端不返回给学生）
- `logs`：两条过程记录（分配、提交）
- 不修改 `submissions` 与 `grades`；成绩在后续汇总时读取 `reviews`

## 2. 我选择检查的质量要求是什么？

- **依据编号及规则**：BR-05「每份提交物由 3 个不同小组评审」＋ BR-17「同一迭代多次提交生成新版本，历史版本保留」，以及 `docs/系统说明.md` 中 M-5「同伴互评」。
- **推导出的质量要求**：分配互评任务时，应以**每个小组每个迭代的最新版本**为评审对象；历史版本不参与评分。
- **对应代码位置**：
  - 分配逻辑：`lib/api.js` **602–604 行**（`store.where('submissions', x => x.projectId === p.id)`）
  - 计分口径：`lib/grades.js` **46–55 行**（`latestSubmissionsOfTeam` 只取同迭代最大版本）

## 3. 我的判断是什么？

**判断：已发现问题。**

**理由**：在「同一小组同一迭代存在多个版本」的条件下，第 602 行遍历的是该项目**全部**提交物（v1、v2…），而不是每个迭代的最新版本；因此会为 v1 和 v2 分别创建 3 个评审任务。而成绩汇总时 `latestSubmissionsOfTeam()` 只统计最新版本，**v1 上的互评不会被计入任何分数**。结果是评审人做了一半无效工作，任务总量翻倍，也容易让人误判“互评份数不足/过多”。

**缺少的信息或需要继续查看的代码**：需求未明确“历史版本是否也需要互评”，但从 BR-17 与计分实现看，历史版本仅用于追溯，不应再评分；需要继续确认 `assignments` 在前端“待评列表”中的展示是否会让评审人看到旧版本（`GET /api/reviews/todo` 直接按 assignment 查提交物，会展示旧版本标题）。

**附带发现（次要）**：第 603 行用 `slice(0, per)` 固定取前 N 个小组，小组数大于 4 时总是同一批小组承担评审，工作量分配不均。

## 4. 如何验证？

- **前置条件**：使用演示数据，第一组在迭代 2 已有 v1、v2 两份提交；共 4 个小组；教师已登录。
- **输入或操作**：教师调用 `POST /api/projects/p1/assign-reviews`，`reviewersPerSubmission=3`。
- **按需求应该得到**：只为「第一组·迭代2 最新版 v2」生成 3 个任务；全项目任务数 = 有效最新提交数 × 3。
- **实际检查**：接口返回 `created` 数量，并查询 `assignments` 中 `submissionId` 的分布——会发现 v1 与 v2 各有 3 条。
- **还必须检查的数据或副作用**：
  - `assignments` 是否存在同一提交物重复分配（应无）
  - `reviews` 提交后 `assignments.status` 是否变为 `submitted`
  - 成绩汇总中 `peerScoreOfTeam` 是否只采纳 v2 的评分（是）
  - `GET /api/reviews/todo` 是否把旧版本暴露给评审人（是）
